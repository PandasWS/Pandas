# 更新日志编写规范

本规范用于编写根 [CHANGELOG.md](../../../CHANGELOG.md) 及对应的 GitHub Release 正文。读者主要是服主、管理员和脚本作者，需要了解本版值得关注的变化，以及升级时要做什么。提交信息的写法另见 [提交规范](commits.md)，发版操作见 [发布正式版](../how-to/publish-release.md)。

## 1. 历史依据与选材原则

`CHANGELOG.md` 开头已经明确：默认不包含 rAthena 官方改动，只精选开发者认为值得重点提出的内容，例如兼容性问题。已发布日志中的代表性写法如下：

| 历史条目 | 体现的取舍 |
| --- | --- |
| v1.2.4 的上游栏目只列两批韩服技改，并注明尚未实装的职业 | 按机制和技改批次概括，交代实际支持范围 |
| v1.2.0 的人工生命体等级、掉线重返副本、属性相克表和掉落概率单位调整 | 优先关注玩法机制、数据含义和运行行为 |
| v1.2.0 的 EP17.2 系列任务和多个副本 | 历史也会精选重要游戏内容，不因实现位于 NPC 脚本而排除 |
| v1.2.0 的 `instance_warpall`，v1.1.19 的 `duplicate`，v1.1.18 的 `petautobonus` | 历史存在脚本接口条目，没有一贯禁止介绍脚本变化 |

本规范在历史“精选上游改动”的基础上统一选材：**机制为主，重要游戏内容精选，普通上游脚本接口和零散 NPC 改动默认省略；影响旧服升级的兼容性变化写入升级提示。** 历史条目用于说明依据与例外，已发布日志保留原样。

## 2. 确定范围与来源

以“上一正式版标签 → 本次待发布提交”为比较范围；准备期间记录审阅所用的目标 SHA，正式发布前补查此后纳入的改动。结合提交、最终代码和数据核对实际行为，不直接将提交标题拼成更新日志。

- **相对上一正式版描述变化。** 开发期间引入又修复的问题通常合并到最终功能说明；仅恢复上一版已有行为的同步修补通常省略。既有指令的内部拆分、重构不写成新增指令。
- **区分来源。** rAthena 提供的能力放入“rAthena 重要更新”；Pandas 自有功能、本地化和兼容适配放入相应的新增、调整或修正栏目。升级提示可包含两方的变化，并按需要注明来源。
- **核对生效条件。** 对受 PRE/RE、客户端日期、编译开关或配置影响的内容，写清必要条件。仅有代码或脚本文件、尚未默认加载的内容，应说明启用方式或暂不收录。
- **只写有依据的信息。** 功能来源、受影响范围、问题编号及贡献者须可追溯到提交、PR、Issue 或实现；不能确认的条目先留在编写记录中，不编造效果、感谢名单或验证结果。

## 3. 上游改动如何取舍

“rAthena 重要更新”用于概括本轮值得服主了解的变化，不逐条复述上游提交。是否收录取决于实际影响，而不是修改了 C++、YAML 还是 NPC 脚本。

| 改动类型 | 处理原则 |
| --- | --- |
| 职业实装、等级或素质上限、技能平衡、战斗计算、状态与冷却保存等机制变化 | 优先收录，相关改动按系统或技改批次合并 |
| 数据库兼容、重要客户端功能、影响运行的稳定性和性能修复 | 有明确影响时收录，写清适用范围与实际效果 |
| 新章节、重要副本、完整玩法系统 | 精选代表性内容；零散任务、NPC、商店或物品补充默认省略 |
| 新增普通脚本指令、查询字段、可选参数等接口扩充 | 默认省略；若构成重要机制，介绍该机制及用途，避免罗列 API |
| 普通脚本修补、NPC 文本调整、文档整理、内部重构和封包结构整理 | 默认省略；重大故障修复或直接影响旧服使用的变化按实际影响收录 |
| 删除指令或常量、改变默认值、数据格式升级等兼容性变化 | 放入“升级提示”，写明受影响对象与迁移方法；涉及脚本也应保留 |

“已弃用但仍可用”与“已经移除”分别表述。弃用提示仅在有明确迁移安排或本轮确有必要提醒时精选收录，不写成升级后立即失效。

这项筛选针对上游摘要。Pandas 自有脚本指令、事件、地图标记等本身就是项目对外提供的功能，仍按用户可见变化正常记录。

## 4. 栏目与归类

沿用以下顺序，只保留有内容的栏目：

| 栏目 | 内容 |
| --- | --- |
| 特别感谢 | 本轮有据可查的贡献与支持；具体条目可沿用“感谢……反馈／修正”的写法 |
| 升级提示 | SQL 升级、自定义数据迁移、配置和接口兼容性、运行环境要求等升级前后需要处理的事项 |
| rAthena 重要更新 | 按上一节筛选的上游机制、重要内容和修复 |
| 新增功能 | Pandas 新增的对外能力 |
| 功能调整 | Pandas 既有能力的行为、配置、使用方式或本地化调整，包括有实际影响的上游实现接替 |
| 缺陷修正 | 相对上一正式版确实存在的问题，以及修复后的行为 |

同一变化尽量只写一次。确需同时介绍机制与迁移时，上游或功能栏目简述效果，具体操作集中放在升级提示。

## 5. 条目的写法

- 一条表达一个完整变化，说明“什么变了、对使用者有什么影响”；需要用户操作时补上做法。沿用“实现／实装／调整／修正”等直接表述，不写提交过程或开发者工作流水账。
- 优先使用玩家和服主熟悉的职业、技能、系统名称；需要精确查找时附英文名或标识符。多个相关技能按职业、机制或技改批次概括，避免只列一串技能常量；译名不确定时保留原名。
- 指令、路径、配置键、常量和版本值使用反引号。问题编号和感谢信息仅在有关联依据时附于条目末尾。
- 修复说明包含必要的触发条件和原问题；性能、完整支持等判断需有相应证据，避免“全面优化”“彻底解决所有问题”等泛化表述。
- 升级提示给出适用条件、受影响对象和可执行的迁移方法。字段含义或参数顺序变化不能仅写“替换名称”；细节较多时链接现有用户文档。

例如，上游移除 `@reload <类型>` 后，条目应说明旧用法及对应替代指令；已有的 `@reloadauradb`、`@reloadlaphinedb` 不因内部实现拆分而列入“新增功能”。

## 6. 版本、日期与升级文件

可以在开发期间积累草稿，发布前根据最终提交范围定稿。版本按新到旧排列，新版放在顶部，沿用现有版本分隔线和标题格式。

- 草稿标题写为 ``## [vX.Y.Z] - `待发布` ``。确认开始执行本次正式发版后，在形成正式发布提交之前，将 `待发布` 替换为本次确认的发布日期 `YYYY-MM-DD`，并清除待定内容；开发阶段整理草稿时保留 `待发布`。日期随 `CHANGELOG.md` 一起定稿，后续构建与 GitHub Release 使用同一份内容。
- 底部比较链接固定为 `v上一正式版...v本次正式版`，例如 `v1.2.4...v1.2.5`。草稿可先写目标标签，标签建立后检查可用性；已确定版本的条目不以持续移动的 `develop` 作为比较终点。
- 社区版对外使用三段版本；程序中的四段版本由开发版 `.1` 调整为正式版 `.0`。升级 SQL 文件名和顶部目标版本沿用三段版本，并与日志引用一致。
- 升级提示使用最终运行包路径，例如 `sql-files\main\upgrades\upgrade_to_1.2.5_main.sql`，而非源码中的 `sql-files/composer/` 路径。注明目标数据库与可选条件，例如仅启用 `use_sql_db` 时才需要的脚本。
- SQL 的汇总、命名、历史文件保留和发布核对遵循 [数据库升级脚本](../how-to/update-database-upgrades.md) 与 [发布正式版](../how-to/publish-release.md)；正式日志中的本轮目标版本不保留开发标记或临时文件名。
- GitHub Release 正文采用本版定稿内容，保留必要链接，避免两处分别维护造成差异。

最小结构示例；实际使用时删除空栏目并填写正式内容：

```markdown
## [v1.2.5] - `待发布`

### 升级提示

- 受影响的使用条件、变化和迁移方法

### rAthena 重要更新

- 精选的机制或重要内容变化

### 功能调整

- Pandas 既有能力的实际变化

```

对应链接定义放在文件末尾：

```markdown
[v1.2.5]: https://github.com/PandasWS/Pandas/compare/v1.2.4...v1.2.5
```

## 7. 定稿检查

1. 比较范围与本次发布一致；相对上一正式版核对新增、调整和修复，来源及生效条件准确。
2. 上游内容经过筛选，相关条目已合并；升级影响和迁移方法没有被精简掉。
3. SQL 路径、文件名、顶部版本及可选条件与运行包一致；版本标题、日期和比较链接完整。
4. 审阅 diff，检查引用与链接；保留既有编码和换行风格，不顺带重排历史日志。发布时复用同一份定稿正文。
