# 开发规范

Pandas 维护相对 rAthena 的长期差异。改动应便于识别本地意图、保留上游更新，并让维护者从代码入口追到实际行为。已有结构参见 [架构概览](../architecture/overview.md)，具体操作参见 [How-to](../how-to/README.md)。

## 功能分支与 PR

`develop` 和 `master` 允许直接快进更新，保留禁止非快进改写和删除的保护。快进要求远端旧提交仍是目标提交的祖先，允许历史中保留 rAthena 同步的 merge commit；不启用禁止 merge commit 的线性历史要求。

功能、修复和上游同步按协作需要使用 PR，便于审查差异及 CI 结果。需要隔离改动时，从最新 `develop` 创建功能分支，并在当前项目仓库内协作。版本号、更新日志及下一轮开发升版可直接在 `develop` 提交和推送；发布时用 `--ff-only` 将 `master` 推进到选定的正式提交，无需额外的发布准备或发布 PR。出现分叉时先处理分叉，不强推覆盖历史。完整步骤见 [发布正式版](../how-to/publish-release.md)。

采用 PR 时，普通改动默认使用 **Rebase and merge**（`gh pr merge --rebase`），保留逐个提交的组织方式；GitHub 会重建提交并生成新的 SHA。rAthena 同步使用 `merge_rathena` 分支并保留 merge commit，通过 PR 合入时选择 **Create a merge commit**；标题格式遵循 [上游同步规范](upstream-sync.md#同步-pr-与汇总合并)。

采用 PR 或直接更新都需完成与改动相称的验证。合入 PR 前核对适用 CI；直接推送前完成本地检查，推送后核对适用 CI，正式发布前完成验收。现有工作流对 `push` 和 `pull_request` 设有路径过滤，未触发的检查应结合改动范围判断是否需要通过 `workflow_dispatch` 补跑，不能把未运行当作成功。提交、推送、创建 PR、合并及发布仍按用户授权范围执行。

## 用宏表达自有功能边界

- 修改 C/C++ 功能时，先在 [pandas.hpp](../../../src/config/pandas.hpp) 查找已有开关和依赖。同一功能的修复、调用点和注册复用同一开关；新增独立功能才建立合适的 `Pandas_*` 宏，放入现有分组并用注释说明行为。
- 替换上游逻辑时，在可维护的范围内保留 `#else` 的上游路径；纯新增逻辑使用 `#ifdef` 包围。宏名表达功能或修复意图，避免无语义的编号。
- 声明、实现、枚举或常量导出、注册表、调用点、结构字段和清理路径必须匹配开关。涉及依赖时显式表达，参考 `Pandas_Support_Future_Execution` 与异步查询开关的关系。
- 检查宏关闭后的编译和行为，尤其是跨文件引用、结构布局、资源释放与返回值。涉及 PRE/RE、数据包版本或关联宏时，选择受影响的组合验证。

宏用于定位和控制功能差异。文档、Python 工具、数据库内容和构建配置使用各自已有机制；不要为了形式在这些文件中加入 C/C++ 宏。仓库仍有无条件差异，关闭宏后的行为应逐功能核对。

## 完成一条实际行为链

从真实调用入口核对输入检查、权限或上下文、实现、状态更新、持久化和反馈。新增内部函数后，还要检查注册与导出，避免出现“实现存在但外部无法调用”的状态。

改动对象生命周期时核对所有权和销毁顺序；改动异步流程时核对线程、连接、结果所有权以及取消、失败和重载路径。针对根因补充验证，优先使用已有入口，避免复制一份实现充当测试目标。

## 文件、生成器与本地化

[.editorconfig](../../../.editorconfig) 规定默认 UTF-8 BOM、文件末尾换行和去除行尾空白；C/C++ 使用 tab，YAML 使用空格。修改旧文件时保留既有编码和换行风格，避免整文件格式噪声。`InjectController` 对源码注入目标还会检查 UTF-8 BOM。

新增常见扩展时优先参考 [tools/python/README.md](../../../tools/python/README.md) 和相应 How-to。`create_*.py` 经 `InjectController` 使用 `PYHELP` 标记定位；保留标记的拼写、编号和唯一性，生成后检查全部 diff，补齐逻辑、文档和验证。

文字修改需区分文件编码、运行时消息语言、SQL 连接字符集和发行版转译。改动控制台原文时同步核对翻译字典和格式占位符；涉及繁体或旧编码数据时沿读取、转换、存储和输出路径验证，具体入口见架构概览。

## 数据与发布联动

- 按相应数据库的 `Footer.Imports` 确认加载次序；已有 `db/pandas/` 补丁层位于模式库之后、用户 `db/import/` 之前，保持用户覆盖的优先级。
- 数据格式变更同时核对解析器、版本号、模板、Pandas 补丁、工具和使用该数据的代码。仅修改主数据文件可能遗漏另一模式或 SQL 数据库用法。
- SQL schema 变更同时考虑全新建库和已有版本升级；发布使用维护好的 `sql-files/composer/` 汇总脚本，按 [数据库升级 How-to](../how-to/update-database-upgrades.md) 处理。
- 新增源码或依赖时检查 CMake 和 Visual Studio 工程的纳入情况。仓库已移除 Autotools 支持，不照抄上游旧的 `configure` 流程。

## 验证与交付

仓库现有验证入口为 [.github/workflows/](../../../.github/workflows/) 和 [tools/integration/](../../../tools/integration/)。其中 [npc_db_validation.yml](../../../.github/workflows/npc_db_validation.yml) 启用 NPC、准备 SQL、构建地图服并执行 `map-server --run-once`，覆盖 PRE/RE 的加载及测试脚本；其他工作流检查编译器、模式、字符集等组合。运行时场景需要对应的行为用例。

按改动选择最小充分验证：文档检查链接和 diff；打包变更用临时目录验证输入到输出；脚本行为尽量接入 `npc/test/ci/`；C/C++ 改动执行相关构建与场景测试。需要修改本地配置的集成脚本在隔离环境运行。记录命令、退出状态及实测范围，未运行的验证说明原因。通过后仅针对新改动或未解决问题追加检查。
